# Universal Agent Engineering Starter

A harness-neutral starting point for serious agent-driven software engineering.

This starter separates:

- **always-loaded policy**
- **detailed engineering quality rules**
- **persistent semantic architecture**
- **project-specific skills**
- **upstream workflow/reference skills**
- **harness-specific adapters**

The goal is to maintain one canonical agent configuration and regenerate the harness-specific views from it.

---

# What is canonical?

Treat these as the source of truth:

```text
.agents/
├── core/
│   └── AGENT_RULES.md
├── skills/
│   ├── code-quality/
│   │   └── SKILL.md
│   └── semantic-architecture/
│       └── SKILL.md
├── architecture/
│   ├── system.md
│   └── ...
├── bootstrap.mjs
└── UPSTREAM_SKILLS.md

```

Generated harness files such as `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, and Cursor rules are **outputs**, not the place to make shared policy changes.

If a generated file says:

```text
GENERATED BY .agents/bootstrap.mjs
```

edit the canonical `.agents/` source instead.

# Core responsibility split

```text
pstack
  → primary engineering process/orchestration
  → architecture workflow
  → TDD
  → verification
  → adversarial review
  → proof

code-quality
  → detailed engineering quality bar
  → anti-reward-hacking constraints
  → design/types/state/concurrency/testing/debugging/etc.

semantic-architecture
  → persistent hierarchical system understanding
  → ownership
  → relationships
  → invariants
  → sources of truth
  → semantic deltas
  → zoom in / zoom out

project-owned skills under `.agents/skills/`
  → product/platform/repository-specific behavior

Matt Pocock skills
  → specialist design/research/review vocabulary and reference
```

Do not mechanically stack overlapping workflows.

Use pstack as the process owner.
Use `code-quality` as the detailed quality bar.
Use `semantic-architecture` when architecture or system semantics may change.
Use project skills for repository-specific concerns.

---


## Single canonical skill location

All repository-owned skills live under:

```text
.agents/skills/
```

This includes:

- `code-quality`
- `semantic-architecture`
- project/platform/product-specific skills
- any other repository-owned skills

Harness-specific directories such as:

```text
.cursor/skills/
.claude/skills/
```

are generated/runtime copies only.

Never maintain the same skill in two canonical locations.

# First-time setup

Make the scripts executable:

```bash
chmod +x setup.sh scripts/verify-agent-setup.sh
```

Then run:

```bash
./setup.sh
```

This will:

1. generate harness adapters,
2. expose project-owned skills to supported harnesses,
3. install pstack when enabled,
4. install cross-runtime pstack skill support when enabled,
5. install selected Matt Pocock skills,
6. record upstream dependency versions in `.agent-deps.lock`,
7. verify the resulting agent setup.

For a local/no-network setup:

```bash
./setup.sh --local-only
```

Optional flags:

```bash
./setup.sh --skip-pstack
./setup.sh --skip-cross-runtime-pstack
./setup.sh --skip-matt
```

Upstream refs may be overridden with:

```bash
PSTACK_REF=<git-ref> ./setup.sh
PSTACK_CROSS_REF=<git-ref> ./setup.sh
MATT_REF=<git-ref> ./setup.sh
```

# Daily editing workflow

## If you want to change general agent behavior

Edit:

```text
.agents/core/AGENT_RULES.md
```

Use this for short, always-relevant rules and triggers.

Examples:

- when a skill should be used,
- instruction precedence,
- non-negotiable engineering behavior,
- completion requirements,
- repository-wide reward signals.

Do **not** put hundreds of detailed engineering rules here.

After editing:

```bash
node .agents/bootstrap.mjs
./scripts/verify-agent-setup.sh
```

This regenerates the root harness instruction files.

# If you want to change semantic-architecture behavior

Edit:

```text
.agents/skills/semantic-architecture/SKILL.md
```

This skill controls how agents:

- ask architecture questions,
- model systems,
- capture invariants,
- record sources of truth,
- define semantic deltas,
- zoom into subsystems,
- zoom back out after implementation,
- record agent-made decisions,
- update persistent system understanding.

The actual project-specific semantic model lives under:

```text
.agents/architecture/
```

The skill describes **how to maintain the model**.
The architecture files describe **this repository's actual system**.

# How to update the architecture model

Start at:

```text
.agents/architecture/system.md
```

Keep the root model system-level.

Create deeper models only when meaningful:

```text
.agents/architecture/
├── system.md
├── sync/
│   ├── system.md
│   └── replication/
│       └── system.md
└── editor/
    └── system.md
```

Use:

```text
.agents/architecture/_templates/system.md
```

as the starting template for a new subsystem model.

Do not pre-create architecture files for every source directory.

Create a deeper model when there is:

- distinct ownership,
- meaningful local invariants,
- important relationships,
- lifecycle/source-of-truth rules,
- repeated rediscovery cost,
- too much detail in the parent model.

The target is **semantic compression**, not documentation coverage.

# How to add a project-owned skill

Create it directly in the canonical skill tree:

```text
.agents/skills/<skill-name>/SKILL.md
```

For example:

```text
.agents/skills/
├── code-quality/
│   └── SKILL.md
├── semantic-architecture/
│   └── SKILL.md
├── project-research/
│   └── SKILL.md
├── privacy/
│   └── SKILL.md
└── deployment/
    └── SKILL.md
```

A good project skill should explain:

1. **when it fires**,
2. **what repository-specific constraints it owns**,
3. **what evidence or verification is required**,
4. **what durable artifacts it may update**.

Avoid duplicating generic engineering guidance already owned by pstack or `code-quality`.

After adding/editing a project skill:

```bash
./setup.sh --local-only
```

This copies canonical skills from `.agents/skills/` into the harness-specific discovery directories supported by the setup.

Do not hand-edit `.cursor/skills/`, `.claude/skills/`, or other generated/runtime skill directories.

Then run:

```bash
./scripts/verify-agent-setup.sh
```

If the skill should be explicitly triggered from the always-loaded policy, also update:

```text
.agents/core/AGENT_RULES.md
```

and regenerate:

```bash
node .agents/bootstrap.mjs
```

# How to add a hook

"Hook" can mean different things depending on the harness.

The rule is:

> Put shared hook policy/logic in a canonical project location, and keep harness-specific registration thin.

Recommended structure:

```text
.agents/
└── hooks/
    ├── README.md
    ├── pre-change/
    ├── post-change/
    └── verify/
```

Examples of useful hooks:

- ensure canonical verification runs before completion,
- reject accidental generated-file edits,
- check architecture-model consistency,
- scan for forbidden dependency direction,
- run secret scanning,
- verify generated harness files are current,
- warn when architecture-sensitive code changes without architecture-model updates.

For executable repository checks, prefer normal scripts:

```text
scripts/
├── verify.sh
├── check-architecture.sh
├── check-generated-agent-files.sh
└── ...
```

Then configure harness-specific hooks to call those scripts.

Do **not** implement the same hook logic separately for Cursor, Claude, Codex, etc.

If a harness requires a special hook configuration file, generate or maintain only the thin registration layer for that harness.

# How to add support for another harness

The canonical place to add generated adapters is:

```text
.agents/bootstrap.mjs
```

Suppose a new harness expects:

```text
NEW_HARNESS.md
```

Add another generated output in `bootstrap.mjs` that points back to the canonical policy.

Prefer:

```text
NEW_HARNESS.md
  → "Read AGENTS.md"
  → "Use canonical skills under .agents/..."
```

over copying the entire policy into a second hand-maintained file.

If the harness requires skills in a harness-specific directory, update `setup.sh` so canonical skills from `.agents/skills/` are copied there.

For example, extend the equivalent of:

```text
install_skill_dir()
```

to include the new harness's skill discovery location.

Then update:

```text
scripts/verify-agent-setup.sh
```

to verify:

- the harness adapter exists,
- it references the canonical policy,
- required skills were installed,
- generated files are current.

Finally run:

```bash
node .agents/bootstrap.mjs
./setup.sh --local-only
./scripts/verify-agent-setup.sh
```

# How to regenerate all harnesses

For policy/adapter-only changes:

```bash
node .agents/bootstrap.mjs
```

This regenerates files such as:

```text
AGENTS.md
CLAUDE.md
GEMINI.md
.cursor/rules/00-project-agents.mdc
```

For project skill changes or harness skill-discovery changes:

```bash
./setup.sh --local-only
```

For a full refresh including upstream pstack/Matt dependencies:

```bash
./setup.sh
```

Always finish with:

```bash
./scripts/verify-agent-setup.sh
```

Recommended full regeneration loop:

```bash
node .agents/bootstrap.mjs
./setup.sh --local-only
./scripts/verify-agent-setup.sh
git diff --check
git diff
git status --short
```

When intentionally updating upstream skill versions:

```bash
./setup.sh
cat .agent-deps.lock
git diff --check
git diff
./scripts/verify-agent-setup.sh
```

Review `.agent-deps.lock` before committing.

Normally commit:

```text
.agents/
AGENTS.md
CLAUDE.md
GEMINI.md
.cursor/rules/
setup.sh
scripts/
.agent-deps.lock
```

Do not commit:

```text
.agent-vendor/
```

unless your repository intentionally vendors upstream dependencies.

Generated adapter files are committed so agents work immediately after checkout, but they should still be regenerated from canonical sources when policy changes.

# Updating upstream pstack or Matt skills

Upstream configuration is documented in:

```text
.agents/UPSTREAM_SKILLS.md
```

To update:

1. choose the new upstream ref,
2. run setup with the override,
3. inspect the installed changes,
4. inspect `.agent-deps.lock`,
5. ensure no upstream instructions conflict with project policy,
6. run verification,
7. commit intentionally.

Example:

```bash
PSTACK_REF=<new-ref> ./setup.sh
MATT_REF=<new-ref> ./setup.sh
```

Do not blindly track upstream changes without review.

# Adding automated architecture guardrails

Semantic architecture becomes more useful when important invariants can be enforced mechanically.

Examples:

```text
Domain must not import provider SDK
Provider types must stop at adapters
Only persistence module may write table X
Cache Y must have explicit invalidation ownership
Generated agent files must match bootstrap output
```

Put executable checks in:

```text
scripts/
```

Then add them to your repository's canonical verification command.

The architecture model describes intent.
Automated guardrails enforce the subset that can be checked cheaply and deterministically.

---

# Recommended repository verification entry point

For a serious project, create one obvious command such as:

```bash
./scripts/verify.sh
```

or:

```bash
pnpm verify
```

It should eventually include the relevant subset of:

```text
repository hygiene
generated-agent-file freshness
architecture guardrails
secret scanning
formatting
lint
type checking
unit tests
module/contract tests
integration tests
build
smoke/E2E verification
```

Agents should not need to memorize a random collection of commands.

# Making changes to this starter itself

Use this workflow:

```bash
# 1. edit canonical source
$EDITOR .agents/core/AGENT_RULES.md
$EDITOR .agents/skills/code-quality/SKILL.md
$EDITOR .agents/skills/semantic-architecture/SKILL.md
$EDITOR .agents/skills/<project-skill>/SKILL.md
$EDITOR setup.sh
$EDITOR .agents/bootstrap.mjs

# 2. regenerate harness adapters
node .agents/bootstrap.mjs

# 3. refresh local project skills
./setup.sh --local-only

# 4. verify
./scripts/verify-agent-setup.sh

# 5. inspect
git diff --check
git diff
git status --short
```

Never fix a generated adapter directly unless the change is intentionally harness-specific and the generator should not own it.

# Quick decision table

| You want to change... | Edit... | Then run... |
|---|---|---|
| Always-on agent behavior | `.agents/core/AGENT_RULES.md` | `node .agents/bootstrap.mjs` |
| Detailed quality rules | `.agents/skills/code-quality/SKILL.md` | bootstrap + verify |
| Architecture workflow | `.agents/skills/semantic-architecture/SKILL.md` | bootstrap + verify |
| Actual project architecture | `.agents/architecture/**/system.md` | repository verification |

| Verification behavior | `scripts/verify*.sh` or project verify command | run verification |

# Quality model

```text
AGENTS.md
  short always-loaded operating contract
        │
        ├── pstack
        │     process/orchestration
        │
        ├── code-quality
        │     detailed reusable quality bar
        │
        ├── semantic-architecture
        │     persistent system understanding
        │
        ├── project skills
        │     repository-specific constraints
        │
        └── upstream specialist skills
              focused reference/vocabulary
```

This separation is intentional.

The always-loaded contract should remain concise.
Detailed rules belong in skills.
Project truth belongs in the architecture model.
Harness-specific files should remain thin generated adapters.

## Lossless split of the original engineering operating system

The original generalized `AGENTS.md` was intentionally decomposed rather than copied wholesale into a skill.

Repository-wide agent operating behavior now lives in:

```text
.agents/core/AGENT_RULES.md
```

Engineering/design quality rules now live in:

```text
.agents/skills/code-quality/SKILL.md
```

The split is auditable via:

```text
.agents/OPERATING_SYSTEM_SPLIT.md
.agents/OPERATING_SYSTEM_SPLIT.json
```

These map every original numbered section to its current canonical home.

When changing this split, preserve all original rules unless you are intentionally deleting or replacing one.
Do not silently compress multiple rules into a summary.
